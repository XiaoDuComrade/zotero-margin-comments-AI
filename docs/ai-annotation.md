# AI 学术标注设计

## 数据流

1. 用户在 Zotero“编辑 → 设置 → 页边批注”中启用 AI，并选择自动检测、Responses 或 Chat Completions 协议，填写 API 地址、API Key、模型、统一颜色和批注数量。
   “补充标注要求”下方的折叠区域显示插件实际使用的默认学者提示词；补充要求不会替换默认提示词，而是追加在其后。
2. 插件启动和打开 PDF 时不会调用外部接口。只有用户点击 Reader 工具栏的 AI 星光按钮并确认后，插件才读取当前 PDF。
3. Responses 模式优先用兼容接口的 `/files` 上传 PDF，并把返回的 `file_id` 交给 `/responses`；若文件端点不可用，则退回内联 Base64 PDF 输入。Chat Completions 模式不上传 PDF，而是发送 Zotero 提取的带 `[PDF_PAGE N]` 标记的文字层。
4. 自动模式在地址以 `/chat/completions` 结尾时直接选择 Chat；否则优先尝试 Responses，并在服务端明确要求 `messages` 或不存在 `/responses` 时回退 Chat。
5. 模型返回物理 PDF 页码、逐字引文、中文学术评论和分类。Responses 使用 JSON Schema；Chat 通过严格提示词约束 JSON，并使用 SSE 流式接收 `reasoning_content` 与正文，最终再解析完整 JSON。
6. 插件从 Zotero Reader 的 `_pdfPages[].chars` 读取文字和 `inlineRect`，规范化空白、引号、破折号和 Unicode 兼容字符后匹配逐字引文。
7. 只有成功匹配的引文才转换为高亮矩形并写入 Zotero。写入使用统一颜色和“AI 学术标注”标签，Notifier 在整批结束后一次提交，避免逐条刷新侧栏。
8. 使用远端 `file_id` 时，插件在请求结束后调用 `DELETE /files/{file_id}`；兼容服务不支持删除时不会影响已生成结果。

## 网页对话模式

1. “用网页对话”是独立开关；开启时星光按钮不调用 API，原有 API 设置保持不变，关闭后即可恢复接口模式。
2. 插件只把提示词作为纯文本复制到系统剪贴板，不复制 PDF 或创建临时文件。用户自行在网页 AI 中上传当前 PDF，再粘贴提示词并发送。
3. 提示词要求回复以 `ZMC_WEB_CHAT_RESULT_V1` 开头，并在 JSON 中原样返回一次性 `request_id`。插件通过由启动脚本提供的特权桥轮询系统剪贴板，并依次兼容 Unicode、纯文本、UTF-8 纯文本与 HTML 格式；优先处理带结果标记的回复，也兼容模型省略标记但返回正确任务编号与 `annotations` 的 JSON。插件不保存或记录其他剪贴板文字，连续读取失败会给出明确错误。
4. 返回 JSON 由本地确定性解析器校验，无需第二次调用模型。随后复用 API 模式的逐字引文定位、预览确认、统一颜色和 Zotero 高亮写入流程。
5. 监听最长 30 分钟；检测到不完整或不相关的新文本时，Reader 会明确显示“已检测到剪贴板变化”，便于区分读取失败与结果格式不正确。再次点击星光按钮、关闭 Reader、禁用相关模式或插件停止时都会取消。

## 可靠性边界

- 模型看到 PDF 不代表插件一定能定位高亮。纯扫描 PDF、损坏的文字层、模型改写引文或跨页引文会被跳过。
- 模型被要求返回从封面开始计数的物理页码，但定位器仍会在其他页查找完全匹配的原文，以容忍页码偏差。
- 同一段原文在一次运行中只写入一条批注，避免重复结果堆叠。
- API Key 保存在本机 Zotero 插件首选项中，不写入运行日志。该存储不是操作系统密码保险库；高安全要求场景建议连接无需外传密钥的本地兼容接口。
- API 的数据保留、训练、费用和地区政策由用户选择的服务商决定；上传前必须由用户确认。
- Reader 会持续显示当前运行阶段与等待秒数；Chat 流式响应会区分“模型正在分析论文”和“正在接收标注结果”。用户可以再次点击 AI 星光按钮取消。测试连接限时 30 秒，连接或流式响应连续 240 秒无新数据时停止等待。
- Chat 接口若明确不支持流式输出，会回退到非流式请求；服务商返回 502、503、504 时显示简短的网关错误，不再把整段 nginx HTML 展示给用户。
- Chat 长文按约 6.4 万字符分批，最多 8 批；在论文后 40% 页面中识别独立的参考文献标题，保留标题所在页并跳过后续纯文献页。多批候选交错合并，避免简单截取导致批注偏向前几批。
- Chat 输出额度不再只按每批候选数计算；长分块会按文字量增加 `max_tokens`，为会先输出 `reasoning_content` 的推理模型保留生成 JSON 的空间。流式结束原因会被保留，以便区分额度耗尽、JSON 截断和服务商空响应；合法的空候选批次不会阻断后续批次。
- Firefox/Zotero 报告 `Error in input stream` 等响应流中断时，错误信息会显示失败批次；已通过缩小单批输入降低服务商中途断流概率。

## 当前接口范围

当前实现支持 OpenAI Responses API PDF 输入、OpenAI 兼容的 Chat Completions 文字输入，以及不经 API 的网页对话剪贴板交换。Chat 文字按约 6.4 万字符分块，最多发送 8 次请求，以限制上下文和意外费用；兼容接口默认采用 SSE 流式返回。Anthropic Messages、Gemini 原生协议以及本地 OCR/版面分析尚未实现。
